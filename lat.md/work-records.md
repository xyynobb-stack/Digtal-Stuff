# Work Records

“我的记录”将用户明确交办的工作按单轮任务保存到本地，供员工在六个月内搜索、复核和导出，同时不阻塞正常聊天。

## Records workspace

左侧导航的“我的记录”页面按当前 Profile 隔离数据，并复用 Profile 的显示名作为员工档案名，避免重复请求员工接口或写死姓名。

页面仅按标题搜索，支持类型、状态筛选、查看原对话、打开来源附件、手工改名和导出。记录库位于 Electron `userData/work-records/work-records.db`，附件只保存暂存路径和元数据，不复制二进制内容。

详情正文拥有独立滚动区域；记录名称在页面内编辑，使用明确的保存和取消操作，不依赖 Electron Renderer 不支持的浏览器原生 `prompt()`。

## Employee workspace continuity

首次员工工作区迁移会在单个 SQLite 事务中把旧 `default` 记录重新归属到已认领的员工 Profile，使“我的记录”和聊天历史同时恢复可见。

迁移先刷新待写快照，只更新匹配源 Profile 的记录及显示名，不复制记录主键或附件行。当前进程随后保留源到目标的归属映射，使迟到的流式收尾或 one-shot 标题快照也直接写入员工 Profile。操作幂等；源 Profile 已无记录时返回零，不影响员工 Profile 后续产生的新记录。该归属切换只发生在员工目标网关健康之后，并受一次性默认工作区认领标记约束。

## Meaningful work filter

普通问候、身份询问等闲聊不会成为工作记录；附件、工具调用、技能、写作模板、项目文件夹或明确工作动词等确定性信号才会建立记录。

是否建立记录及任务分类不额外调用模型，避免记录功能增加首字延迟。所有判定均在统一 Chat 消息时间线上完成，因此 Dashboard 与 Legacy 使用同一规则。

## Turn snapshots

每个带 `turnId` 的用户消息最多对应一条记录，流式文本不逐 token 入库，只在状态、步骤、附件或最终结果发生结构变化时提交快照。

Renderer 通过单向 IPC 发送快照；主进程在短窗口内按记录 ID 合并最新 revision，并在一个 SQLite WAL 事务内批量 upsert。手工标题单独存储并始终覆盖后台生成的本地标题。应用启动时未结束任务会标记为已中断，超过 180 天的记录会清理。

主回答完成后，Renderer 可通过现有 Dashboard WebSocket 异步调用无状态 `llm.oneshot`，一次生成记录标题和 1 至 5 条业务步骤。调用不绑定 live session、不修改聊天历史，也不阻塞用户看到回答；迟到结果按 `turnId` 和输入指纹匹配，失败时保留确定性的本地摘要。只有本次挂载期间实际经历运行态的新任务具备增强资格，恢复旧会话不会批量重放 one-shot 请求。

## Progressive titles

记录先用中文本地规则生成可搜索的临时标题，常用任务使用稳定名称，其余任务提取用户请求首句或附件名。主回答完成后由 one-shot 语义标题替换临时标题，用户可随时手工修正。

标题更新不参与主聊天请求，也不写回会话状态；因此记录命名失败或改名冲突不会影响模型调用。手工标题优先级最高，后台迟到结果不能覆盖。标题搜索使用大小写归一化的子串匹配，不扫描正文、步骤或附件内容。

## Business steps

工作记录默认展示普通用户可理解的业务步骤，不直接展示工具名、函数参数、JSON、内部路径或异常堆栈。

one-shot 使用用户请求、附件名称、脱敏后的执行类别和最终回答生成业务步骤。模型调用不可用或返回格式无效时，本地按读取附件、处理分析、检索资料、保存结果和返回答案等确定性类别生成兜底步骤；历史技术详情仅在用户主动展开时显示。

## Deletion safety

用户可在详情页通过应用内确认框永久删除单条工作记录；删除记录不会删除原对话或来源文件。

主进程删除时先移除尚未落盘的同 ID 快照，再在同一 SQLite 事务中写入删除墓碑并级联删除记录、附件和步骤。墓碑会拒绝流式收尾、延迟 one-shot 或 Renderer 重发的更高 revision 快照，因此异步结果不能把已删除记录重新创建；墓碑随六个月保留周期清理。

Renderer 同时按请求代次接收列表刷新，并在当前进程内过滤已确认删除的 ID，防止删除前发起、删除后才返回的旧列表响应让项目短暂重现。删除失败时解除过滤并重新读取数据库。
